## Gitのorphanブランチの作り方

https://zenn.dev/yoichi/articles/git-create-orphan-branch

### そもそもorphanブランチとは？

> orphan = 孤児

- **親コミットを持たない**ブランチ。既存の履歴と一切つながらない「別の歴史」を同じリポジトリ内に作れる

### orphanブランチの作り方

```sh
git switch --orphan <new-branch>
```

## RunbookとPlaybook

### 概要

特定のサービス名ではなく、運用の一般用語（ドキュメントの種類）。

| | Runbook | Playbook |
|---|---|---|
| 目的 | 決まった作業を**実行**する手順書 | 障害の**調査**（影響範囲・根本原因の特定）の手順書 |
| 例 | 「サービスを再起動する手順」 | 「デプロイ失敗時: 何を見て原因を絞り込むか・誰に報告するか」 |

- Playbook で原因を特定 → その原因を直す Runbook を呼ぶ関係
- 定義は AWS Well-Architected を参照
  - Runbook: [OPS07-BP03 Use runbooks to perform procedures](https://docs.aws.amazon.com/wellarchitected/latest/operational-excellence-pillar/ops_ready_to_support_use_runbooks.html)
  - Playbook: [OPS07-BP04 Use playbooks to investigate issues](https://docs.aws.amazon.com/wellarchitected/latest/operational-excellence-pillar/ops_ready_to_support_use_playbooks.html)

### SREとしてどうこれらを活用できる？

- 障害対応の MTTR（復旧までの平均時間）を縮める。Google は「事前に playbook に記録しておくと、場当たり対応より MTTR が約 3 倍改善する」と書いている（[SRE book ch.1](https://sre.google/sre-book/introduction/)）
- アラートごとに Runbook をリンクしておけば、深夜でも迷わず動ける／属人化を防げる
- Runbook の手順が固まったら**自動化の候補**になる（トイル削減）

## ⭐️Google Cloud: Service account key rotation

https://docs.cloud.google.com/iam/docs/key-rotation

- 大前提: **そもそも鍵を使わない**方法（Workload Identity Federation など）を優先する
- 使うなら**少なくとも 90 日ごと**にローテーション。漏洩の疑いがあれば即時
- 手順: 対象の鍵を特定 → 新しい鍵を作成 → アプリ側を差し替え → 古い鍵を**無効化して様子見** → 削除
  - いきなり削除せず「無効化」を挟むのは、壊れたら**すぐ戻せる**ようにするため
- 期限付きの鍵でローテーションを代用するのは NG（差し替え漏れで障害になる）


「期限付きの鍵でローテーションを代用するのは NG」について、差し替え漏れで障害になるのはそれはそう。だけど、期限を設定しないのはキーが外部に漏れた際のリスクが大きすぎる気がする...このあたりは、絶対的な正解があるわけではなく、それぞれの組織のセキュリティ要件に拠りそうな気はする。

## マジックミラー効果

> 抽象側からは具体例が見えるが、具体側からは抽象側が見えない状態を表す比喩

- 例: 抽象化できる人は「それは〇〇の一例だね」とわかるが、具体の中にいる人からは共通の構造が見えない
