## ⭐️Docker: 特権コンテナ

### 特権コンテナとは

前提: **コンテナは仮想マシンではなく、ホストと同じカーネルを共有した「ただのプロセス」**。ホスト側で `ps aux` すれば見える。隔離しているのは、カーネルがそのプロセスに掛けている制限だけ。

```
ホスト（カーネルは1つ）
  └─ コンテナ = ただのプロセス
       ├ namespace   … 何が「見える」か（他プロセス / ファイル / ネットワーク）
       └ capability 他 … root として何が「できる」か（mount、ルーティング変更 …）
```

つまり**コンテナは壁で囲まれた部屋ではなく、目隠し（namespace）と手錠（capability）をされたプロセス**。`--privileged` は**手錠だけ外す**。

**capability** = 昔は「全部できる / 何もできない」の二択だった root を、約41枚の札に割ったもの。

```
ホストの root  [■■■■■■■■■■■■■■■■■■■■] 41枚
通常コンテナ   [■■■■■■■□□□□□□□□□□□□□] 14枚 ← mount の札が無い
特権コンテナ   [■■■■■■■■■■■■■■■■■■■■] 41枚
```

```sh
docker run --rm alpine mount -t tmpfs none /mnt              #=> permission denied（rootなのに）
docker run --rm --privileged alpine mount -t tmpfs none /mnt #=> 通る
```

危険な理由もここ。手錠が外れるとホストのディスクが見えて mount できる = `mount /dev/sda1 /mnt` の一発でホストのファイルを全部読み書きできる。

### Docker-in-Dockerとは

コンテナの中で Docker デーモンを動かすこと（`docker:dind`）。デーモンは overlayfs を mount し、cgroup を作り、iptables を張るので **`--privileged` が必要**（公式 README に "required" と明記）。無しだと `mount: permission denied` で exit 1。

### Cloud Runと特権コンテナ

**使えない。** ランタイム契約に "There is no Cloud Run equivalent to Docker's `--privileged` mode." と明記。capability の付与も seccomp の差し替えも不可。

**一言でいうと: Cloud Run は「コンテナを動かす場所」であって「コンテナを作る場所」ではない。**

## ⭐️GitHub App: JWT / installation access token / registration token

参考（すべて公式）:
- [Generating a JWT for a GitHub App](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-json-web-token-jwt-for-a-github-app)
- [Authenticating as a GitHub App installation](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation)
- [REST API: Self-hosted runners](https://docs.github.com/en/rest/actions/self-hosted-runners)

「自作の Bot にリポジトリへ PR を立てさせたい」を例に。

```
秘密鍵 .pem（App 作成時に1度だけDL）
   │ RS256 で署名
   ▼
JWT（最大10分）  … 「この App 本人です」としか言えない。リポジトリは触れない
   │ POST /app/installations/{installation_id}/access_tokens
   ▼
installation access token（1時間・ghs_…）  … ここで初めてリポジトリを触れる
   │
   ▼
PR を立てる / git clone
```

### なぜ2段階なのか

秘密鍵が一番危ないから。具体的には:

- **期限が無い** —— 自分で作り直すまで永久に有効
- **全インストール先に効く** —— 3つの org に入れていれば3つとも
- **下位トークンを何度でも作れる** —— これ1つあれば App のできること全部ができる

漏れたら App ごと乗っ取られ、止めるには鍵を再生成して全環境に配り直すしかない。だから秘密鍵はトークンを作るときだけ使い、**毎回のAPI呼び出しには「10分で切れる JWT」「1時間で切れる・そのインストール先しか触れないトークン」を使う**。下に降りるほど、漏れたときの被害が小さくなる。

| | 期限 | できること |
| --- | --- | --- |
| 秘密鍵 (.pem) | 無期限 | JWT に署名する |
| JWT | 最大10分 | App 自身の情報 / 次のトークンの発行 |
| installation access token | 1時間 | そのインストール先のリポジトリ操作 |

期限は自分で決められない。公式がこう定めている。

> Your JWT must be signed using the `RS256` algorithm.
> （`exp` は）The time must be no more than 10 minutes into the future.

> Installation access tokens expire after 1 hour.

### これは何の技術？

**machine-to-machine (M2M) 認証** —— 人間が出てこない、サービス同士の認証。

### registration token は別物

名前が似ているだけで**上の流れとは無関係**。GitHub Actions の **self-hosted runner を登録する整理券**。

> Use this token to register a runner on a repository. (…) The token expires after one hour.

```
installation access token（または PAT）
   │ POST /repos/{owner}/{repo}/actions/runners/registration-token
   ▼
registration token（1時間）
   │ ./config.sh --url https://github.com/owner/repo --token <token>
   ▼
runner が登録される
```

**まとめ**: JWT = トークンを取りに行くためだけのもの / installation access token = 普段API を叩くのはこれ / registration token = runner 登録専用、系統が違う。
