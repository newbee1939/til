## Cloud SQL: ssl_mode

- Cloud SQLのSSL接続オプションは、`require_ssl`から`ssl_mode`へ移行が進んでいる
    - Admin APIのリファレンス（[IpConfiguration](https://docs.cloud.google.com/sql/docs/postgres/admin-api/rest/v1beta4/instances#ipconfiguration)）で、`requireSsl`の説明文が `"Use sslMode instead."` から始まっている（＝deprecated扱い）
    - 同ページに `"The value of sslMode has priority over the value of requireSsl."` とあり、**両方指定されたら`sslMode`が勝つ**

| 値 | 挙動 | 旧`require_ssl` |
| --- | --- | --- |
| `ALLOW_UNENCRYPTED_AND_ENCRYPTED` | 平文もSSLも許可（デフォルト） | `false` |
| `ENCRYPTED_ONLY` | SSL接続のみ許可 | `false` |
| `TRUSTED_CLIENT_CERTIFICATE_REQUIRED` | SSL接続＋有効なクライアント証明書が必須 | `true` |

### 注意：`require_ssl=true`は「暗号化必須」ではない

前提として、TLSには**役割の違う2種類の証明書**がある。

- **サーバ証明書** … サーバが「私が本物のCloud SQLです」と名乗るためのもの。暗号化するなら必ず使われるので、クライアント側は特に何も持たなくてよい
- **クライアント証明書** … 逆に、**繋ぎに来た側が「私は許可されたクライアントです」と名乗る**ためのもの。Cloud SQL側で事前に発行し、アプリに配っておく必要がある（＝お互いが証明書を出し合う **mTLS / 相互TLS**）

この区別を踏まえると、

- `ENCRYPTED_ONLY` … 通信は暗号化するが、**相手が誰かは証明書では問わない**（認証はDBのユーザー/パスワードに任せる）
- `TRUSTED_CLIENT_CERTIFICATE_REQUIRED`（= 旧`require_ssl=true`） … 上に加えて**クライアント証明書も必須**

つまり旧`require_ssl=true`は「平文を弾く」だけでなく「証明書を持たないクライアントを全部弾く」設定。公式も `"If you want to enforce SSL/TLS without enforcing the requirement for valid client certificates, then use the sslMode flag instead of the legacy requireSsl flag."` と書いている。

- **平文を弾きたいだけなら`ENCRYPTED_ONLY`**。深く考えず`TRUSTED_CLIENT_CERTIFICATE_REQUIRED`にすると、証明書を配っていないアプリが軒並み接続不能になる

## GitHub Actions: runnerのリソースについて

> buildが同一runner上でCPU/ネットワーク帯域を奪い合っている可能性が高いです

- GitHub-hosted標準runner(2コア)だと、3並列buildの恩恵がリソース競合で相殺されやすい構造だと思われる

### 前提：runnerのスペック

[GitHub-hosted runners reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners) の "Standard GitHub-hosted runners for private repositories" の表より、`ubuntu-latest`は

| Processor (CPU) | Memory (RAM) | Storage (SSD) |
| --- | --- | --- |
| 2 | 8 GB | 14 GB |

- **8 GB = メモリ（RAM）**、**14 GB = ディスク容量（SSD）**。別物なので混同しない
- publicリポジトリだと同じ`ubuntu-latest`でも 4 CPU / 16 GB / 14 GB と倍のスペックになる

### CIのリソースとは？

runnerという1台のVMを、並列buildが分け合っている。競合するのは主に4つ。

- **CPU（論理CPU数）** … コンパイル・minifyなど「計算そのもの」
- **メモリ（8 GB）** … 並列数だけプロセスが立つので山分けになる。使い切ると **OOM**（Out Of Memory）でプロセスがカーネルに強制終了される。CIで突然 `Exit code 137` で落ちるのがこれ
- **ディスクI/O・容量（14 GB）** … *I/O* は読み書きの速さ。`npm install`の展開や`docker build`のレイヤー書き込みは大量の小さいファイル書き込みで、CPUではなく**ディスク待ち**になりやすい。*容量*も14 GBしかなく、3並列分のイメージやキャッシュを置くと `No space left on device` で落ちる
- **ネットワーク帯域** … `docker pull`や依存パッケージの取得。VM単位で共有なので、並列にしても総ダウンロード時間は縮まない

CPUについては [2026/07/09](./09.md) の話がそのまま効く。`2 vCPU` = **同時に走れるプロセスは2つまで**という天井なので、1job内で3並列にしても3本目は並列（parallelism）にならず、タイムスライスで奪い合う並行（concurrency）にしかならない。コンテキストスイッチのコストも乗る。

```
論理CPU0: │ B1 │ B3 │ B1 │ B3 │ ...
論理CPU1: │ B2 │ B2 │ B2 │ B2 │ ...
           └─ 同時に走れるのは2本まで
```

### 対処

- **jobを分ける**：job単位で別VMが割り当たるので、3jobに分ければ 2 vCPU × 3台になる
- **larger runnerを使う**：1jobのまま並列度を上げたいなら vCPU を増やす（課金増）。[Larger runners reference](https://docs.github.com/en/actions/reference/runners/larger-runners) より 2〜96 vCPU から選択可能
- **並列度をvCPU数に合わせる**：**CPUバウンド**（＝処理時間の大半をCPU計算が占める仕事。対義語は、通信やディスクの「待ち」が大半を占める**I/Oバウンド**）なら 並列数 = 論理CPU数 が基本
    - I/Oバウンドな処理は待っている間CPUが空くので、vCPU数より多い並列度でも効果が出る。逆にCPUバウンドで増やしすぎるとコンテキストスイッチ分だけ遅くなる
