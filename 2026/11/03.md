## ⭐️OAuth: 全体像

OAuth は、ユーザーの許可を得て、アプリがユーザーの代わりに API を呼べるようにする仕組み。MCP では次の対応になる。

| OAuth の役割 | MCP では |
| --- | --- |
| リソースオーナー | ユーザー |
| クライアント | MCP クライアント（Claude Code など） |
| 認可サーバー | トークンを発行するサーバー |
| リソースサーバー | MCP サーバー |

ゴールは、MCP サーバーを呼ぶためのアクセストークンを得ること。

```text
1. [DCR]  クライアントを登録            → client_id
2. [PKCE] ブラウザで認可ページを開く（code_challenge 付き）
3.        ユーザーがログインして「許可」
4.        redirect_uri に転送される     → 認可コード
5. [PKCE] 認可コード + code_verifier    → access_token, refresh_token
6.        MCP サーバーを呼ぶ（Authorization: Bearer <access_token>）
7. [更新] 期限切れなら refresh_token   → 新しい access_token
```

1〜5 と 7 の相手は認可サーバー。MCP サーバーとやり取りするのは 6 だけ。

## ⭐️DCR

Dynamic Client Registration（RFC 7591）。クライアントが実行時に自分を登録し、`client_id` をもらう。MCP はクライアントもサーバーも不特定多数なので、事前に手で登録できない。

```http
POST /register
{ "redirect_uris": ["http://localhost:3000/callback"] }

→ { "client_id": "s6BhdRkqt3" }
```

`redirect_uris` は、手順 4 で認可コードを受け取る宛先。認可サーバーは登録済みの宛先にしか転送しないので、攻撃者のサーバーに認可コードを送らせることはできない。

## ⭐️PKCE

Proof Key for Code Exchange（RFC 7636）。認可コードを盗まれても、トークンに交換させない。

- `code_verifier`: クライアントが毎回作る乱数。手元に隠しておく（例: `dBjftJeZ4CVP-...`）
- `code_challenge`: verifier の SHA-256。見られてもよい（例: `E9Melhoa2Owv...`）

```text
手順 2: challenge を送る    → 認可サーバーが認可コードとセットで覚える
手順 5: verifier を送る     → 認可サーバーがハッシュして challenge と一致すれば発行
```

認可コードはブラウザを通るので盗まれうる。verifier はブラウザを通らないので盗めず、challenge からも逆算できない。だから盗んだ認可コードは使えない。

## ⭐️リフレッシュトークン

アクセストークンの期限が切れたとき、再ログインなしで新しいものをもらうためのトークン（RFC 6749）。

| | アクセストークン | リフレッシュトークン |
| --- | --- | --- |
| 送り先 | MCP サーバー（毎回） | 認可サーバー（更新時だけ） |
| 寿命 | 短い | 長い |

よく送るほど漏れやすいので、アクセストークンは短命にする。代わりにリフレッシュトークンで更新する。

```http
POST /token
grant_type=refresh_token&refresh_token=...&client_id=s6BhdRkqt3
```

リフレッシュトークンは長命なので、使うたびに新しいものに交換し、古いものは無効にする（ローテーション、RFC 9700 Section 4.14）。
