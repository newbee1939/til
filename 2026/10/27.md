## ⭐️eMudhraの中間CAの秘密鍵が公開された証明書から復元可能と判明⁠⁠した件

インドの認証局 eMudhra の中間 CA 8 個の秘密鍵が、実質「1〜255 のどれか」だった。
証明書に載っている公開鍵から 256 回以下の総当たりで秘密鍵がわかり、どのドメインの証明書でも偽造できる状態だった。

### 1. 証明書の仕組み

#### 署名

鍵は 2 本 1 組。秘密鍵で押した判（署名）は、対応する公開鍵でしか確かめられず、秘密鍵を持つ人にしか作れない。
ただし公開鍵だけでは「誰の鍵か」がわからない。攻撃者も鍵を作って「私が bank.example です」と名乗れる。

#### 証明書

「この公開鍵は bank.example のもの」と、CA（認証局）が署名した身分証。顔写真にあたるのが公開鍵。
証明書は公開情報で、サーバは接続してきた誰にでも渡す。入っているのは公開鍵だけで、秘密鍵は入っていない。

#### チェーンとトラストアンカー

CA 自身は親の CA が保証する。親をたどった終点がルート。

```
[ルート証明書]  emSign ECC Root CA - G3      ← トラストアンカー（無条件に信じる起点）
   │ ルートの秘密鍵で署名
   ▼
[中間証明書]   EM DV TLS CA - G3B など      ← 今回、秘密鍵が漏れたのはここ
   │ 中間の秘密鍵で署名
   ▼
[サーバ証明書] bank.example
```

- ルート証明書は自分で自分に署名している。署名では信頼を証明できないので、「最初から信じる」と決めて手元に置く。これがトラストアンカー
- 中間を挟む理由: ルートの鍵が漏れると、配布済みの全端末からそのルートを消すしかない。だからルートの鍵は金庫（HSM: 鍵を外に出さずに署名だけする専用機器）にしまい、普段の発行は中間でやる
- トラストアンカーの一覧（トラストストア）は 1 つではない。OS、ブラウザ（Chrome / Firefox）、言語・ツール（Python certifi、Node、Java cacerts、curl、Electron アプリ…）がそれぞれ別に持っている

#### クロス署名

同じ中間の鍵に、別のルートからも署名してもらうこと。証明書は 2 枚になるが、鍵は 1 つ。
今回の中間は Sectigo のルート（AAA Certificate Services）からもクロス署名されていた。そのため emSign のルートを消すだけでは、Sectigo 経由の道が残る。

### 2. HTTPS 接続でやっていること

```
クライアント ── ClientHello「bank.example に繋ぎたい」 ──▶ サーバ
クライアント ◀── サーバ証明書 + 中間証明書 ─────────────── サーバ
クライアント ◀── ここまでのやり取りに、サーバ証明書の秘密鍵で押した署名 ── サーバ
```

クライアントは次の 2 つを確かめる。

1. 証明書は本物か: 中間 → ルートとたどってトラストストアまでつながるか。名前・期限は正しいか、失効していないか
2. 相手は本人か: 届いた署名を、サーバ証明書の公開鍵で検証する

公衆 Wi-Fi のように経路上の誰かが通信を読み書きできる環境でも安全なのは、この検証があるから。
裏を返すと、検証を通る偽の証明書を作れれば、経路上の攻撃者は警告なしで割り込める。

### 3. 壊れた証明書を止める仕組み

| 仕組み | 中身 | 効く範囲 |
| --- | --- | --- |
| 失効（CRL / OCSP） | CA が「この証明書は取り消した」と公開する | 確認しないクライアントが多い |
| CRLSet（Chrome）/ OneCRL（Firefox） | ブラウザが失効情報を端末に直接配る | そのブラウザだけ。数時間で効き、再起動も不要 |
| CT（Certificate Transparency） | 発行された全証明書を公開ログに記録させる。ブラウザはログに載っていない証明書を拒否する | ブラウザだけ。curl などは確認しない |
| トラストストアの更新 | ルートや中間をファイルから消す | ソフトの更新 → 配布 → 再起動まで届いて初めて効く |

### 4. 今回の事件

#### なぜ公開された証明書から秘密鍵がわかるのか

楕円曲線暗号の鍵の関係はこれだけ。

```
公開鍵 Q = d × G     d: 秘密鍵（整数）  G: 誰でも知っている固定の点
```

- d が 384 ビットの巨大な数なら、Q から d を逆算するのは事実上不可能。ここに安全性がかかっている
- 今回は d < 256 だった。1×G から 255×G まで計算し、証明書に書いてある Q と一致するものを探せば一瞬で終わる（値は 4, 56, 115 など）
- 暗号（P-384）は破られていない。どんなに頑丈な金庫でも、暗証番号が「4」なら意味がないという話

原因（eMudhra の説明）: 2025-04 のキーセレモニー（監査人立ち会いで鍵を作る儀式）で手順を変更した際、スクリプトのバグで弱い鍵がもう 1 組作られた。ラベルが似ていたため、強い鍵と取り違えて使ってしまった。根本原因はまだ調査中。

#### 攻撃者にできること

1. 自分の鍵で「bank.example の証明書」を作り、漏れた中間の鍵で署名する
2. Wi-Fi や偽の DNS 応答で、被害者の通信を自分に向ける
3. 2 章の検証はすべて通る（チェーンはつながり、署名に使う秘密鍵も攻撃者の手元にある）

対象はすべてのドメイン。8 個のうち 2 個はコード署名用で、正規の発行元を装ってマルウェアに署名することもできた。

#### 守られたもの、危ないもの

- ブラウザは無事: 問題の中間 CA の証明書は CT ログに 1 件も載っていなかった。偽の証明書もログに載らないので弾かれる。加えて Chrome と Firefox は、報告を受けた当日のうちに鍵ごとブロックした
- 危ないのはブラウザ以外: curl、pip、Node、Java、Go/Rust 製のバイナリ、Electron アプリ、IoT 機器など。多くは CT も失効も確認しないので、トラストストアを更新するまで偽の証明書を信じてしまう
- 実際に悪用されたかどうかは不明

#### 時系列（UTC）

| 日付 | 出来事 |
| --- | --- |
| 2025-04-30 | 弱い鍵を持つ中間 CA が作られる |
| 2026-10-17 | 研究者が報告。同日中に Chrome（CRLSet）と Firefox（OneCRL）がブロック |
| 10-18〜19 | eMudhra と Sectigo が該当する証明書を失効させる。Android にもブロックを配信 |
| 10-19〜22 | Apple と Microsoft がブロック。Go / Python / Node.js / Java などが修正版を公開 |
| 10-20 | Mozilla がルート（G3）ごと削除すると発表 |
| 10-22 | eMudhra が SSL/TLS 証明書事業からの撤退を発表 |
| 10-27（PDT） | Chrome がルート（G3）を削除する予定（配信完了は未確認） |

#### ルートを消すと、正規のサイトも巻き込まれる

- G3 ルートの下には、有効な正規の証明書が約 3 万枚ある（99.9% は米国の大学向けの InCommon 経由）。別の CA の証明書に入れ替えないとエラーになる
- Sectigo のルートまで消すと Sectigo の正規証明書が全滅するので、そちらはクロス署名の失効と、中間の鍵単位のブロックで対処した
- 教訓は「信頼を足すのは簡単、取り消すのは大変」

eMudhra は撤退の理由として「SSL/TLS は売上の約 1%」「規制対応コストの増加」「無料の CA の台頭」を挙げた。jxck 氏はこれを CA としての責任放棄だと批判している。

### 5. 自分（SRE）がやること

- 棚卸し: OS の ca-certificates、コンテナのベースイメージ、certifi（venv ごと）、Node、Java、Go/Rust のバイナリ、CI、各種エージェント
- 更新: 修正版に上げる → イメージを再ビルド → 再起動 / 再デプロイ。ここまでやって初めて効く
- 確認: ブラウザではなく、実際にアプリが使う経路で試す

```sh
curl https://dv-g3b-emudhra.we-have-a-problem.com/
# 「unable to get local issuer certificate」で止まれば対策済み。繋がったら危険
```

curl は自分の CA バンドルのルートまでチェーンをたどろうとする。G3 がバンドルから消えていれば、つながらずにエラーで止まる。

- 禁止: エラーを回避するために `-k` や `verify=False` で検証を切らない。偽の証明書を通す状態に自分から戻すことになる
