## 全体像: エージェントに社内アプリを使わせたい

下の 3 つは別々の話ではなく、「エージェントに社内 Wiki を読ませたい」ときに順に出てくる困りごとと、その答えです。

| 困ること | 答え |
| --- | --- |
| エージェントはログインできない | Managed OAuth |
| エージェントは事前に登録されていない | DCR |
| 中継役がトークンを使い回したくなる | token passthrough の禁止 |

ビルの入館にたとえると、登場人物はこうなります。

| OAuth の用語 | 今回 | ビルでたとえると |
| --- | --- | --- |
| Resource Owner | ユーザー | 社員 |
| Client | エージェント | 社員に頼まれたお使い |
| Authorization Server | Cloudflare Access | 受付 |
| Resource Server | 社内アプリ | 部屋 |
| トークン | トークン | 入館証（誰の代理か・どこ用か・期限が書いてある） |

```
ユーザー --(1)--> エージェント --(4)--> 社内アプリ
   |                   ^
  (2)                 (3)
   v                   |
Cloudflare Access -----+

(1) 「Wiki を読んで」と頼む
(2) 自分でログインして「このエージェントに任せる」と許可する
(3) トークン（入館証）を発行する
(4) トークンを見せてアクセスする
```

ユーザーのパスワードが通るのは (2) だけで、エージェントには渡りません。エージェントが持つのは (3) のトークンだけです。

## Access向けのマネージドOAuthとは

https://blog.cloudflare.com/ja-jp/managed-oauth-for-access/

一言で言うと、受付（Access）が、社員の OK をもらって、お使い（エージェント）に入館証（トークン）を出す仕組みです。

そのままでは、エージェントはログイン画面で止まります。ユーザーのパスワードを知らないからです。かといって、パスワードを教えるわけにもいきません。

そこで、ログインはユーザーが自分でやり、「このエージェントに任せる」と許可だけ出します。Access はそれを見て、エージェントにトークンを渡します。パスワードは渡さず、入館証だけ渡すのが肝です。

```
1. Agent → 社内アプリ                    ← 401（入館証がない。受付はあっち）
2. Agent → Access に自分を登録（DCR）     ← client_id
3. ユーザーがブラウザでログインして許可     ← トークン
4. Agent → 社内アプリ（トークン付き）     ← 200
```

- 以前: エージェント用の合鍵（サービスアカウント）で入っていた → 誰が頼んだか記録に残らない
- 今: 入館証に社員の名前が入っている → 本人が入れる部屋にしか入れず、記録にも本人が残る

## DCRとは

https://www.rfc-editor.org/rfc/rfc7591

一言で言うと、エージェントが受付に自分で名前を登録する仕組みです。（Dynamic Client Registration）

そのままでは、上の 3 に進めません。受付は登録済みの相手（`client_id` = 登録番号を持つ相手）にしか入館証を出さないからです。ふつうは開発者が事前に管理画面で登録しますが、エージェントは初めてのビルにいきなり来ます。

そこで、登録をその場の API 1 回で済ませます。

```
POST /register
{ "client_name": "My Example Client", "redirect_uris": ["https://client.example.org/callback"] }

→ 201 Created
{ "client_id": "s6BhdRkqt3", ... }
```

- 注意: 名前は自己申告なので、登録番号があるだけでは信用されない。信用の根拠は、あくまで 3 のユーザーの許可

## token passthroughとは

https://modelcontextprotocol.io/specification/2025-06-18/basic/security_best_practices#token-passthrough

一言で言うと、中継役（MCP サーバー）が、受け取ったトークンをそのまま次の API に回すことです。MCP の仕様で禁止されています。

例えば、MCP サーバーが裏で GitHub API を呼ぶとします。Client から GitHub 用のトークンを受け取って、そのまま GitHub に見せれば楽です。しかしそれでは、MCP サーバーは何も確かめない素通しになります。盗まれたトークンでも通り、誰が頼んだかも追えません。

そこで、入館証の「どこ用か」（JWT の `aud`）を見ます。MCP サーバーは自分用のものだけ受け取り、GitHub には自分で取った入館証で行きます。

```
✗ Client --[GitHub 用]--> MCP サーバー --[同じトークン]--> GitHub API
○ Client --[MCP サーバー用]--> MCP サーバー --[自分で取ったトークン]--> GitHub API
```
