## 全体像: エージェントに社内アプリを使わせたい

下の 3 つは別々の話ではなく、「エージェントに社内 Wiki を読ませたい」ときに順に出てくる困りごとと、その答えです。

| 困ること | 答え |
| --- | --- |
| エージェントはログインできない | Managed OAuth |
| エージェントは事前に登録されていない | DCR |
| 中継役がトークンを使い回したくなる | token passthrough の禁止 |

ビルの入館にたとえると、登場人物はこうなります。

| OAuth の用語 | 今回 | ビルでたとえると |
| --- | --- | --- |
| Resource Owner | ユーザー | 社員 |
| Client | エージェント | 社員に頼まれたお使い |
| Authorization Server | Cloudflare Access | 受付 |
| Resource Server | 社内アプリ | 部屋 |
| トークン | トークン | 入館証（誰の代理か・どこ用か・期限が書いてある） |

```
ユーザー --(1)--> エージェント --(4)--> 社内アプリ
   |                   ^
  (2)                 (3)
   v                   |
Cloudflare Access -----+

(1) 「Wiki を読んで」と頼む
(2) 自分でログインして「このエージェントに任せる」と許可する
(3) トークン（入館証）を発行する
(4) トークンを見せてアクセスする
```

ユーザーのパスワードが通るのは (2) だけで、エージェントには渡りません。エージェントが持つのは (3) のトークンだけです。

## Access向けのマネージドOAuthとは

https://blog.cloudflare.com/ja-jp/managed-oauth-for-access/

一言で言うと、受付（Access）が、社員の OK をもらって、お使い（エージェント）に入館証（トークン）を出す仕組みです。

そのままでは、エージェントはログイン画面で止まります。ユーザーのパスワードを知らないからです。かといって、パスワードを教えるわけにもいきません。

そこで、ログインはユーザーが自分でやり、「このエージェントに任せる」と許可だけ出します。Access はそれを見て、エージェントにトークンを渡します。パスワードは渡さず、入館証だけ渡すのが肝です。

### 何が「Managed」なのか

OAuth の仕組み自体は、ふつうの OAuth と同じです。違うのは、受付（名簿・許可画面・入館証の発行）を Cloudflare が代わりに用意してくれる点です。マネージド DB の「マネージド」と同じ意味です。

|  | 通常の Access | 自前の OAuth | Managed OAuth |
| --- | --- | --- | --- |
| 想定する相手 | ブラウザを使う人間 | エージェント | エージェント |
| 入館証がない相手への返事 | ログイン画面へ案内 | 401 + もらい方の案内 | 401 + もらい方の案内 |
| 受付を用意する人 | Cloudflare | アプリの開発者 | Cloudflare |
| アプリの改修 | 不要 | 必要 | 不要（1 クリック） |

- 通常の Access だけだと、エージェントはログイン画面に案内されても操作できず、そこで詰む
- 自前の OAuth だと、社内アプリ 1 つずつに受付を作り込むことになる
- Managed OAuth は、通常の Access の手軽さのまま、エージェントが通れる入口を足したもの

### 流れ

会話にするとこうなります。Access は社内アプリの手前に立つ門番なので、返事をするのは Access です。

```
(1) 門前払いされる
  エージェント「Wiki を見せて」
  Access      「401。入館証がないよ。もらい方はここに書いてある」

(2) 名前を登録する（DCR）
  エージェント「初めて来ました。My Example Client です」
  Access      「名簿に書いた。あなたの番号は client_id = s6Bh...」

(3) ユーザーに許可をもらう
  エージェント「（ユーザーへ）この URL をブラウザで開いて」
  ユーザー    「（Access へ）ログインした。このエージェントに任せる」
  Access      「（エージェントへ）はい、入館証（トークン）」

(4) 入る
  エージェント「Wiki を見せて。入館証はこれ」
  Access      「200。どうぞ」
```

- 以前: エージェント用の合鍵（サービスアカウント）で入っていた → 誰が頼んだか記録に残らない
- 今: 入館証に社員の名前が入っている → 本人が入れる部屋にしか入れず、記録にも本人が残る

## DCRとは

https://www.rfc-editor.org/rfc/rfc7591

一言で言うと、エージェントが受付の名簿に、自分で名前を書く仕組みです。（Dynamic Client Registration）

なぜ名簿が要るかというと、受付は (3) で相手を知っている必要があるからです。

- ユーザーに「My Example Client に任せますか？」と名前を見せる
- 許可の結果を、名簿に書かれた届け先にだけ送る（他人に横取りさせない）

ふつうは、開発者が事前に管理画面で名簿に書きます。「Google でログイン」を組み込むときに、Google Cloud Console で client ID を作るのがこれです。

しかしエージェントは、どのアプリにつなぐか事前にわかりません。世界中の受付に前もって登録しておくのは無理です。

そこで、初めて来たその場で、API 1 回で名簿に書きます。

```
POST /register
{
  "client_name": "My Example Client",                        ← 許可画面に出る名前
  "redirect_uris": ["https://client.example.org/callback"]   ← 許可の結果の届け先
}

→ 201 Created
{ "client_id": "s6BhdRkqt3", ... }                           ← 名簿の番号。以後これを名乗る
```

- 注意: 名前は自己申告なので、番号を持っているだけでは信用されない。信用の根拠は、あくまで (3) のユーザーの許可

## token passthroughとは

https://modelcontextprotocol.io/specification/2025-06-18/basic/security_best_practices#token-passthrough

一言で言うと、中継役（MCP サーバー）が、受け取ったトークンをそのまま次の API に回すことです。MCP の仕様で禁止されています。

例えば、MCP サーバーが裏で GitHub API を呼ぶとします。Client から GitHub 用のトークンを受け取って、そのまま GitHub に見せれば楽です。しかしそれでは、MCP サーバーは何も確かめない素通しになります。盗まれたトークンでも通り、誰が頼んだかも追えません。

そこで、入館証の「どこ用か」（JWT の `aud`）を見ます。MCP サーバーは自分用のものだけ受け取り、GitHub には自分で取った入館証で行きます。

```
✗ Client --[GitHub 用]--> MCP サーバー --[同じトークン]--> GitHub API
○ Client --[MCP サーバー用]--> MCP サーバー --[自分で取ったトークン]--> GitHub API
```
