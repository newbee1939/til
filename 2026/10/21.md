## ⭐️GitHub Actions: JIT runner（Just-In-Time）

1 ジョブだけ動いて消える self-hosted runner。

1 ジョブ = ワークフローの `jobs:` の 1 つが 1 回実行されること。matrix なら組み合わせごと、Re-run も別ジョブ扱い。

### トークンとの関係

2026/09/18 の流れ（秘密鍵 → JWT → installation access token）の先で、runner の登録方法が 2 つに分かれる。違いは「誰が、いつ登録するか」。

```
registration token（登録は runner がやる）
  管理役: .../registration-token  → 整理券をもらう（1 時間有効）
  runner: config.sh --token 整理券 → runner が GitHub に「登録して」と頼む
  runner: run.sh                  → ジョブを待つ。終わっても次のジョブを待ち続ける

JIT config（登録は管理役がやる）
  管理役: .../generate-jitconfig  → この時点で GitHub 側に登録が済み、認証情報が返る
  runner: run.sh --jitconfig 認証情報 → 登録の手順なしで即起動。1 ジョブ終えたら登録解除
```

- registration token: 「登録してよい」という整理券。登録作業は runner 側に残る
- JIT config: 登録済みの runner の認証情報そのもの（base64）。runner はファイルに書き出して起動するだけ

### 手動登録との関係

手動登録（Settings → Actions → Runners → New self-hosted runner）も左側と同じ registration token。違いはトークンを出すのが App ではなく、画面の人間なだけ。

「手動か API か」と「使い捨てか常駐か」は別の軸。

| | 常駐（permanent） | 使い捨て（ephemeral） |
| --- | --- | --- |
| registration token（手動 / API） | ○ | ○ `--ephemeral` |
| JIT config（API のみ） | × | ○ |

### 外部から登録する意味

```
GitHub ──ジョブ来た──▶ 管理役（鍵あり）
                         │ JIT config を発行
                         ▼
                      runner（鍵なし）→ 1 ジョブ実行 → 消える
```

- runner に GitHub App の鍵を置かない。ジョブを乗っ取られても鍵は漏れない
- 毎回まっさらな環境。前のジョブの秘密情報が残らない
- ジョブが来た分だけ作れる（オートスケール）

これを Kubernetes でやる GitHub 公式の仕組みが ARC（Actions Runner Controller）。

参考:
- https://docs.github.com/en/actions/reference/runners/self-hosted-runners
- https://docs.github.com/en/rest/actions/self-hosted-runners#create-configuration-for-a-just-in-time-runner-for-an-organization
- https://docs.github.com/en/actions/concepts/runners/actions-runner-controller
- https://github.com/actions/runner/blob/main/src/Runner.Listener/Runner.cs （`--jitconfig` の処理）

## SARIF

静的解析の結果を書く共通 JSON 形式（OASIS 標準）。「どのファイルの何行目に、どんな問題があるか」の一覧。

- GitHub に送ると Security タブ（Code scanning）にアラートとして出る
- 送るには `security_events: write` 権限のトークンが要る

参考: https://docs.github.com/en/code-security/code-scanning/integrating-with-code-scanning/sarif-support-for-code-scanning

## ⭐️php2shell（CVE-2026-109618 / 109619）

PHP 本体の脆弱性。ログイン不要で、外から 1 つの HTTP リクエストを送るだけでサーバー上でコマンドを実行される（RCE）と言われている。CVSS 9.2。詳細は未公開で、以下はリーク情報ベース。

### どういうバグか: use-after-free（UAF）

解放したメモリを、まだ使い続けてしまうバグ。ホテルで言えば、チェックアウトした部屋の鍵を持ち続けている状態。

```
           メモリ                     PHP の手元
① 使用中   [ PHP のデータ   ]  ←──  住所メモ
② 解放     [ 空き           ]  ←──  住所メモ（消し忘れ）
③ 再利用   [ 攻撃者のデータ ]  ←──  住所メモ
④ PHP が住所メモの先を読む → 攻撃者のデータを自分のものと信じて動く → 処理を乗っ取られる
```

### 入口: Session Upload Progress

ファイルアップロードの進み具合をセッションに記録する機能。既定で有効。

- POST に `PHP_SESSION_UPLOAD_PROGRESS` という項目を付けるだけで動く
- アプリのコードより前に PHP が処理する → アップロード機能が無いサイトでも、WordPress でも Laravel でも届く

### 攻撃の流れ

```
攻撃者（ログイン不要）
  │ POST（multipart + PHP_SESSION_UPLOAD_PROGRESS）
  ▼
Web サーバー（Apache / nginx）
  ▼
PHP 本体 ← ここで UAF。アプリのコードに届く前
  │ 乗っ取り
  ▼
www-data としてコマンド実行
  ├ .env を読む       → DB パスワード / API キーが漏れる
  ├ Web シェルを置く  → いつでも再侵入、ページ改ざん
  └ IAM ロールを使う  → クラウドの他のリソースへ広がる
```

### 対策

- 修正版を当てる（10/21 公開）。パッケージの changelog に CVE 番号があるかで確認
- `session.upload_progress.enabled=0` は応急処置。2 つ目のバグは別経路（multipart の解析処理）との説があり、これだけでは防げない

参考:
- https://blog.flatt.tech/entry/php2shell
- https://lilting.ch/en/articles/php2shell-session-upload-progress-uaf
- https://www.php.net/manual/en/session.upload-progress.php

## reap: 刈り取り

実在する英単語。元は農業の「（作物を）刈り取る、収穫する」。

- reap the benefits: 成果を得る（比喩）
- Grim Reaper: 死神（大鎌で魂を刈る者）
- IT では「終わったプロセスの後始末」。終了した子プロセスは親が `wait()` するまで「ゾンビ」として残る。`wait()` で回収することを reap と呼ぶ

参考: https://man7.org/linux/man-pages/man2/wait.2.html
