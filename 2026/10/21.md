## reap: 刈り取り

実在する英単語。元は農業の「（作物を）刈り取る、収穫する」。

- reap the benefits: 成果を得る（比喩）
- IT では「終わったプロセスの後始末」。終了した子プロセスは親が `wait()` するまで「ゾンビ」として残る。`wait()` で回収することを reap と呼ぶ

参考: https://man7.org/linux/man-pages/man2/wait.2.html

## ⭐️php2shell（CVE-2026-109618 / 109619）

PHP 本体の脆弱性 2 件。ログイン不要の POST 1 つで、サーバー上で好きなコマンドを動かされる（RCE = Remote Code Execution）。CVSS 9.2（10 点満点、9.0 以上は最上位の Critical）。2026/10/21 に修正版が出た。

- 対象: Web リクエストを処理する PHP すべて（PHP-FPM / mod_php / php-cgi / FrankenPHP / LiteSpeed）。バージョンは 5.x〜8.x の修正版未満すべてと考えておく（flatt の見立て。原因のコードは 5.2〜5.4 ごろからある）
- 一番危ないのは mod_php。アプリのコードより前に攻撃が通ることが実証済み

### 経緯

```
10/20  PHP が「重大な脆弱性 2 件の修正版を 10/21 に出す」と予告（詳細は伏せる）
       同じ日に情報がリーク。「php2shell」と呼ばれ広まる
10/21  国内で 50 以上の組織が修正版を待たずにサービスやサイトを止める
       （BASE、コドモン、Cygames、厚労省など）
       22:40 JST ごろ 修正版と詳細を公開（予定の 23:00 より少し早い）
       公開後、watchTowr（おとりサーバーで観測）や Cloudflare が攻撃の試みを観測
```

- 実際の被害は情報が割れている（Patchstack は「複数の侵害を確認」、他社は未確認）。CISA の悪用確認済みリスト KEV には未登録（10/22 時点）
- 予告から公開までの約 1 日で、リークと推測が広まり、各社がサービスを止めるか判断を迫られた

### どこまで分かっている？

| | 中身 | 出どころ |
| --- | --- | --- |
| 分かっている | バグの仕組み（下の 2 つ）。メモリ切れの起こし方（巨大なヘッダーなどを詰めた multipart POST） | PHP 公式の GHSA |
| 実証済み | Session Upload Progress 経由の攻撃が成立する | 公式 / flatt の独自検証 |
| 分かっていない | 乗っ取りまでの最後の手順（メモリ配置の仕込み方）。他の攻撃経路（公式はわざとぼかしていて、他にもあると見られる） | 非公開 |
| 真偽不明 | ネット上の PoC（攻撃コード）。動くかは検証されておらず、マルウェア混入の恐れもある | 第三者 |

### 2 つのバグ

どちらも同じ形。1 つのリクエストが壊れたデータをメモリに残し（Producer）、別のリクエストがそれを使ってしまう（Consumer）。両方そろって初めて攻撃が成立する。

```
攻撃リクエスト A ──▶ 壊れたデータが残る（Producer）
攻撃リクエスト B ──▶ それを正しいと信じて使う（Consumer）──▶ 乗っ取り
```

| CVE | 一言で | 中身 |
| --- | --- | --- |
| 109618 | メモリ切れで後片付けが壊れる | わざとメモリを使い切らせる → PHP が処理を途中で打ち切る → 準備途中のデータを、後片付けが正しいものとして扱う |
| 109619 | 解放済みメモリを次のリクエストが使う | 途中で打ち切られると、解放済みメモリを指す変数が残る → 同じワーカーの次のリクエストがそれを使う（use-after-free = UAF） |

### 攻撃の流れ（109619 の Session Upload Progress 経路）

- ptr = メモリの番地を書いておく変数（ポインタ）。ここではリクエストをまたいで残るグローバル変数
- 係 = メモリの貸し出し係（アロケータ）。空き一覧を持つ
- ワーカー = リクエストを順番に処理する PHP のプロセス。何度も使い回される

```
① 1 回目: 攻撃者がアップロード（multipart）を送る
   ptr ──▶ 0x7000 [ 進捗データ ]

② 途中でエラー（メモリ切れなど。攻撃者が起こす）→ 処理を打ち切り   ← バグ
   メモリは解放されるが、ptr を消す処理は飛ばされる
   ptr ──▶ 0x7000 [ 空き ]            係の空き一覧: [0x7000]

③ 2 回目: 攻撃者のデータが 0x7000 に入る                          ← 攻撃者が突く
   PHP は届いたデータを置くため係からメモリを借りる → 係は空いている 0x7000 を貸す
   ptr ──▶ 0x7000 [ 攻撃者のデータ ]

④ 進捗処理が古い ptr を使う（use-after-free）                      ← バグ
   攻撃者のデータを正しい進捗データだと信じて動く → 処理の行き先を乗っ取られる

⑤ Web サーバーのユーザー（www-data など。root ではない）でコマンドが動く
   → .env の秘密を盗む / 裏口（Web シェル）を置く / クラウドへ広がる
```

① ② は公式の説明どおり。③ ④ の細かい手順（メモリ配置の仕込み方）は非公開なので、UAF の典型的な流れで書いている。

### 対策

修正版に上げる。公式: "There are no complete mitigations, updating is the only safe choice."

- 修正版: 8.5.12 / 8.4.27 / 8.3.36 / 8.2.35。ディストリ / LTS ベンダーには事前にパッチが渡っている
- 8.1 以前: 公式の更新なし。ベンダーのバックポートか、公式の 7.4 / 8.0 / 8.1 向けパッチでソースビルド
- remi（rpms.remirepo.net）は当日更新なし。ディストリのパッケージかソースビルドへ
- 8.2 は 2026/12/31 でサポート終了

すぐ上げられないとき（一部の経路を塞ぐだけ。安全にはならない）:

109618（メモリ切れ）
- `memory_limit=-1` をアプリが上書きできない形で設定（`php_admin_value` など）
- `post_max_size` を小さく（8M、アップロードありなら 32M）。プロキシでもリクエストの大きさ・項目数を制限
- メモリ上限は cgroup で。`RLIMIT_AS` / `RLIMIT_DATA` はメモリ切れを起こしてバグを招くので使わない

109619（解放済みメモリ）
- `session.upload_progress.enabled=0`。`php.ini` か FPM pool に書く（`ini_set()` / `.user.ini` は効かない）
- 8.5 は `fatal_error_backtraces=0`
- リクエストごとの設定で警告が出るもの（無効・非推奨の設定）を消す。`@` や `display_errors` で隠しても無意味
- 攻撃者が起こせる致命的エラーやタイムアウトを直す

共通（GHSA / flatt）
- multipart を使わないなら、プロキシで遮断する
- 性能が落ちてよければ `pm.max_requests=1`（1 リクエストごとにワーカーを作り直す → 壊れたデータが次に残らない）
- `max_input_nesting_level` を下げる（入れ子の深い入力を拒否）

設定を変えたら全ワーカーを再起動する。

### やること（flatt の推奨順）

1. 更新するまでの時間を稼ぐため、必要ならシステムを止める
2. PHP を更新する
3. 攻撃を受けていないかログを調べる
4. 侵害されていたら、盗まれたデータの範囲を調べる
5. サーバーの権限（IAM ロールなど）を確認し、他への横展開がないか見る
6. ログが記録・保全されているか見直す（改ざんされると調査できない）
