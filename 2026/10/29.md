## ⭐️eMudhraの中間CAの秘密鍵が公開された証明書から復元可能と判明⁠⁠した件

インドの認証局 eMudhra の中間 CA 8 個で、秘密鍵が 1〜255 のどれかだった。
255 回試せば秘密鍵がわかり、どのドメインの証明書でも偽造できた。

### 1. 用語

- 秘密鍵: 本人だけが持つ巨大な整数。デジタル署名を作る
- 公開鍵: 秘密鍵から計算する値。署名を検証する。公開鍵から秘密鍵は逆算できない（今回ここが崩れた）
- 証明書: 「このドメインの公開鍵はこれ」に CA がデジタル署名したもの
- トラストストア: 端末が最初から信じるルート証明書の一覧。アプリごとに別（Chrome は自前、curl は `/etc/ssl/cert.pem`、Node は本体に埋め込み）

```
[ルート]  emSign ECC Root CA - G3   ← トラストストアに入っている
   ▼ 署名
[中間]   EM DV TLS CA - G3B など    ← 今回、秘密鍵が割れた
   ▼ 署名
[サーバ]  example.com
```

中間 CA はどのドメインの証明書でも発行できる。1 つ割れれば全ドメインが偽造可能になる。

### 2. HTTPS 接続で確かめること

```
ブラウザ                                       example.com
  │ ① 鍵の材料 ──────────────────────────────▶ │
  │ ◀── ② 鍵の材料。両者が同じ共通鍵を計算      │
  │ ◀── ③ 証明書（サーバ + 中間）               │
  │ ◀── ④ ①〜③への署名（サーバの秘密鍵で）     │
  │ ⑤ 検証 a・b が通ったら HTTP を開始           │
```

- ①② 鍵交換: 一時的な公開鍵を送り合い、自分の秘密鍵と組み合わせて同じ共通鍵を計算する。盗聴者には計算できないが、相手が本物かはまだ不明
- a: ③ を上へ順に検証し、最後はトラストストアにあるルートの公開鍵で検証 →「example.com の公開鍵はこれ」
- b: ④ をその公開鍵で検証 →「相手は example.com 本人」

### 3. 今回の攻撃

```
あなた ◀──▶ 攻撃者（偽 Wi-Fi など）◀──▶ 本物の example.com
```

1. 割り出した中間 CA の鍵で、「example.com の公開鍵 = 攻撃者の公開鍵」という偽証明書を作る
2. 接続を横取りして偽証明書を返す
3. a は本物の CA の署名なので通る。b は攻撃者自身の鍵なので通る
4. URL も鍵マークも正常なまま、通信を全部読まれ、書き換えられる

### 4. 原因と影響

- 原因: 鍵生成スクリプトのバグ。本来は約 116 桁の数
- なぜ割れるか: 公開鍵は「秘密鍵の回数だけ同じ計算を繰り返した結果」。255 通り試せば一致する
- ブラウザは当日に対策済み。危ないのは独自に検証する curl・pip・Node・Java・Go（Linux）
- Mozilla / Google は G3 ルートを削除。eMudhra は証明書事業から撤退
