## Docker Hardened Images

Docker が保守する、最小構成のコンテナイメージ。

- 不要なパッケージを削り（distroless 版はシェルもない）、デフォルトで非 root ユーザーで動く
  - distroless: アプリ本体と実行に要るライブラリだけを入れ、シェル・パッケージマネージャ・OS ツールを抜いたイメージ。DHI の通常（runtime）版はこれにあたる
  - シェルや apt が要るビルド・開発用には `-dev` 版が別にある。本番で中を調べるときは `docker debug` でデバッグ用のコンテナを横付けする
- 継続的にスキャンとパッチを行い、既知の CVE をほぼゼロに保つ
- 署名付きの SBOM（中身の部品一覧）と provenance（どうビルドしたかの記録）が付く
- Community 版は無料（Apache 2.0）。CVE 修正の SLA などが付くのは有料版

## Laravel: trustProxies

どのプロキシから来た `X-Forwarded-*` を信じるかを決める設定（`bootstrap/app.php`）。

```php
->withMiddleware(function (Middleware $middleware): void {
    $middleware->trustProxies(at: ['10.0.0.0/8']);            // この IP から来たときだけ信じる
    $middleware->trustHosts(at: ['^example\.com$']);          // 想定外の Host は拒否
})
```

- 普段の流れ: ブラウザ → LB → アプリ。LB が「元の Host は example.com」と `X-Forwarded-Host` に書いて渡し、アプリはそれを見て URL を組み立てる
- `at: '*'` は「誰が書いた `X-Forwarded-*` でも信じる」設定。LB を通らずアプリに直接届く経路があると、攻撃者が自分で書いたヘッダーもそのまま信じてしまう

  ```
  curl http://<アプリの IP>/forgot-password -H 'X-Forwarded-Host: evil.com' -d 'email=victim@example.com'
  ```

  → アプリは自分を evil.com だと思い込み、パスワードリセットのメールに `https://evil.com/reset/<トークン>` を載せる。メールは被害者のアドレスに本物のサービスから届く（攻撃者が変えられるのはリンクのドメインだけ）。リセットのフォームはログイン不要でメールアドレスを入れるだけなので、攻撃者が被害者のアドレスを入れれば、アプリはそのアカウント宛てに送る。被害者がそのリンクを踏むと、トークン付きの URL が evil.com に届き、攻撃者はそのトークンを本物の example.com で使ってパスワードを書き換える
- `trustHosts` は「自分のホスト名はこれだけ」と許可リストを持たせる設定。Host が evil.com のリクエストはその時点で拒否するので、偽装されても URL は作られない
