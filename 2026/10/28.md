## ⭐️eMudhraの中間CAの秘密鍵が公開された証明書から復元可能と判明⁠⁠した件

インドの認証局 eMudhra が運営する中間 CA 8 個（1 個につき秘密鍵は 1 つ）で、秘密鍵の値がすべて 1〜255 のどれかだった。
最大 255 回試せば秘密鍵がわかり、どのドメインの証明書でも偽造できる状態だった。

### 1. 証明書の仕組み

#### 署名

- 秘密鍵 = 本人だけが持つ、ただの巨大な整数。署名を作るのに使う
- 公開鍵 = 秘密鍵から計算して作る値。誰に配ってもよく、署名の検証に使う
- 秘密鍵から公開鍵は一瞬で計算できるが、公開鍵から秘密鍵を逆算するのは事実上不可能。これが安全性の土台（今回はここが崩れた）

```
署名: データのハッシュ（指紋）を取る → 指紋と秘密鍵から「署名値」を計算する
検証: 受け取ったデータの指紋を取る → 指紋・署名値・公開鍵を決まった式に入れ、成り立つか確かめる
```

- データを 1 ビットでも変えると指紋が変わり、式が成り立たなくなる（改ざんがわかる）
- 式を満たす署名値は秘密鍵がないと作れない（署名したのが秘密鍵の持ち主だとわかる）
- ただし公開鍵だけ見ても「誰の公開鍵か」はわからない。攻撃者も自分の公開鍵を「example.com の公開鍵です」と言って配れる。これを保証するのが証明書

#### 証明書

「このドメインの公開鍵はこれ」という情報に、CA（認証局）が署名したもの。

```
┌ example.com の証明書 ─────────────────────────────────────┐
│ Subject  : example.com                                     │
│ 公開鍵   : example.com のサーバの公開鍵                       │  ← この部分が署名の対象
│ Issuer   : Cloudflare TLS Issuing ECC CA 3（発行した CA）     │
├────────────────────────────────────────────────────────────┤
│ 署名     : 上の部分に、Issuer の秘密鍵で付けた署名値            │
└────────────────────────────────────────────────────────────┘
```

証明書は公開情報で、中身は公開鍵だけ。対応する秘密鍵は example.com のサーバだけが持つ。

#### チェーンとトラストアンカー

Issuer の公開鍵が本物かは、さらに上の CA の署名で保証する。上へたどった終点がルート（`openssl s_client -connect example.com:443 -showcerts` で確認）。

```
[ルート]  SSL.com TLS ECC Root CA 2022   ← トラストアンカー。端末に最初から入っている
   ▼ ルートの秘密鍵で署名
[中間]   SSL.com TLS Transit ECC CA R2
   ▼ この中間の秘密鍵で署名
[中間]   Cloudflare TLS Issuing ECC CA 3
   ▼ この中間の秘密鍵で署名
[サーバ]  example.com
```

- ルートは自分で自分に署名しているので、署名では信頼を証明できない。「最初から信じる」と決めて端末に置く。これがトラストアンカー
- 端末（Mac や Chrome）が持っているのは、ルート証明書（名前と公開鍵）の一覧だけ。CA の秘密鍵は CA の金庫（HSM という専用機器）の中にしかない。公開鍵で検証はできるが、証明書の発行はできない
- 中間 CA の秘密鍵は、どれか 1 つが漏れただけで、世界中のどのドメインの証明書でも発行できてしまう。中間 CA ごとに担当ドメインが決まっているわけではないため
- 中間 CA の役割は、ルートの代わりに日々の証明書発行を行うこと
  - ルートの秘密鍵は中間 CA の証明書を作るときしか使わない。普段はネットから切り離して保管できるので、漏れる機会がほぼない
  - 中間 CA の秘密鍵が漏れても、その中間だけ無効にすれば済む。ルートが漏れたら、世界中の端末のトラストストアから消して入れ替えるしかない
- eMudhra のチェーン: `emSign ECC Root CA - G3 → EM DV TLS CA - G3B など → サーバ証明書`

トラストアンカーの一覧（トラストストア）はアプリごとに違う。今回の対応が面倒なのはこのため。

| 使う側 | トラストストア |
| --- | --- |
| Safari など Mac アプリ | macOS のシステムキーチェーン |
| Chrome / Firefox | 自前で持つ |
| `/usr/bin/curl` | `/etc/ssl/cert.pem` |
| Node.js | Node 本体に埋め込まれた一覧（`node -p "tls.rootCertificates.length"` で件数を表示）。Node 自体の更新が必要 |
| Go | macOS / Windows は OS に任せる。Linux は Go 自身が検証 |

#### 失効（revocation）

「この証明書はもう信じない」というリスト。ブラウザは自前のリスト（OneCRL、CRLSet）をすぐ配れるが、curl や Go（Linux）などは基本的に見ない。

### 2. Mac の Chrome で example.com を開くと

ゴールは 2 つ。「途中で盗み見られない通信路を作ること」と「その通信路の相手が本当に example.com だと確かめること」。

```
Chrome                                                           example.com のサーバ
  │ ① 「example.com に繋ぎたい」+ 合鍵の材料 A ──────────────────▶ │
  │ ◀──── ② 合鍵の材料 B。ここで両者が同じ合鍵を計算し、以降は暗号化   │
  │ ◀──── ③ 証明書（サーバ証明書 + 中間証明書）                      │
  │ ◀──── ④ ①〜③のやり取り全体に、サーバの秘密鍵で付けた署名          │
  │ ⑤ 検証（下の a と b）。どちらかが失敗したら、ここで止めて警告画面    │
  │ ⑥ 「GET / をください」+ Cookie ────────────────────────────────▶ │
  │ ◀──── ⑦ HTML                                                    │
```

#### ①② 合鍵を作る

送るのは材料だけで、合鍵そのものは送らない。それでも両者が同じ合鍵を計算できる仕組み（鍵交換）。途中で盗み見ている人は、材料だけでは合鍵を計算できない。

ただしこれだけでは、経路上の攻撃者が「自分が example.com です」と割り込んで、攻撃者と合鍵を作らされる恐れがある。暗号化されていても、相手が攻撃者なら意味がない。だから ③〜⑤ で相手を確かめる。

#### ⑤-a 証明書は本物か

下から順に、1 つ上の証明書に入っている公開鍵で署名を確かめていく。

1. example.com の証明書の署名を、Cloudflare 中間証明書の公開鍵で検証 →「Cloudflare の中間 CA が、example.com の公開鍵はこれだと保証した」
2. Cloudflare 中間証明書の署名を、SSL.com Transit 中間証明書の公開鍵で検証
3. SSL.com Transit 中間証明書の署名を、SSL.com ルートの公開鍵で検証
4. その SSL.com ルートが Chrome Root Store に入っているか確かめる
5. 証明書の名前が example.com か、期限内か、失効していないかも確かめる

ここまでで言えるのは「example.com の公開鍵はこれ」まで。今話している相手が本人かは、まだわからない。

#### ⑤-b 相手は本人か

証明書は公開情報なので、誰でもコピーして送れる。証明書を送ってきたこと自体は、本人である証拠にならない。

そこで ④ の署名を、証明書に入っている example.com の公開鍵で検証する。

- この署名は、example.com のサーバの秘密鍵がないと作れない
- 署名の対象は今回のやり取り（①② の合鍵の材料を含む）なので、過去の署名を盗んで使い回すこともできない

通れば「合鍵を一緒に作った相手 = example.com の秘密鍵の持ち主」と確定する。

#### ⑥⑦ HTTP を始める

a と b が通って初めて、Chrome は合鍵で暗号化した HTTP リクエスト（「トップページをください」、ログイン状態を表す Cookie など）を送る。サーバは HTML を返し、画面に表示される。鍵マークはこの状態を表す。

#### 今回の事件で何が起きうるか

攻撃者は example.com のサーバや DNS を乗っ取るわけではない。本物のサーバはそのまま動いている。
攻撃者が入り込むのは「あなたと本物のサーバの間の経路」。例: カフェに置いた偽の Wi-Fi、乗っ取った家庭用ルーター。

準備（攻撃者の手元で、事前に）:

```
1. 公開されている eMudhra 中間証明書から公開鍵を取り出し、秘密鍵を総当たりで割り出す（最大 255 回）
2. 自分で鍵ペアを作る
3. 「example.com の公開鍵 = 攻撃者の公開鍵」と書いた偽の証明書を作り、割り出した中間 CA の秘密鍵で署名する
```

当日（あなたが偽 Wi-Fi で example.com を開く）:

```
あなたの PC                     攻撃者（偽 Wi-Fi）                   本物の example.com
  │ ① example.com に繋ぎたい ──────▶ │ 横取りして、自分が応答する
  │ ◀── ② 偽の証明書 + 攻撃者の秘密鍵で署名 │
  │ ③ 検証                             │
  │    a: eMudhra 中間 → emSign ルート    │
  │       （トラストストアにある）→ 通る   │
  │    b: 攻撃者は自分の秘密鍵を持つ → 通る │
  │    → 攻撃者を example.com だと思い込む │
  │ ④ ID・パスワード・Cookie ────────▶ │ 合鍵で復号して中身を読む
  │                                      │ ⑤ 本物と正規に接続し、同じリクエストを転送 ──▶ │
  │                                      │ ◀──────────────────── ⑥ 本物の HTML ── │
  │ ◀── ⑦ HTML（必要なら書き換えて返す） │
```

- どこにも飛ばされない。アドレスバーは `https://example.com` のまま、鍵マークも正常、表示されるのも本物のページ。だから気づけない
- 攻撃者は真ん中で全部を読み書きできる。パスワードや Cookie を盗む、ページに JavaScript を仕込む、`pip install` で落とすファイルをマルウェアに差し替える、など
- 普段なら ③-a で失敗する。攻撃者が自作した証明書には、信頼された CA の署名がないから。今回は漏れた中間 CA の秘密鍵で「本物の CA の署名」を付けられてしまった

### 3. 今回の事件

秘密鍵はただの整数で、本来は 384 ビット（10 進で約 116 桁）の範囲から無作為に選ぶ。今回は 8 個とも値が 255 以下だった。256 ビットではなく、値そのものが 256 未満。8 ビット（1 バイト）に収まる大きさしかなかった。原因は鍵生成スクリプトのバグ。

- なぜ漏れたか: 公開鍵は「規格で決まった基準点を、秘密鍵の回数だけ足し合わせた点」。基準点は誰でも知っている。回数が 116 桁もあれば逆算は宇宙の寿命でも無理だが、最大 255 回なら「1 回足した点、2 回足した点…」と計算して証明書の公開鍵と比べれば一瞬で見つかる
- 誰が危ないか: ブラウザは CT（発行された証明書の公開ログ）と失効リストで当日に防げた。危ないのは curl・pip・Node・Java・Go（Linux）など
- その後: Mozilla と Google は G3 ルートごと削除する。eMudhra は SSL/TLS 証明書事業から撤退

#### Go の対応

通知から約 7 時間半で修正版（Go 1.27.3 / 1.26.10）を出した。

- Linux では Go 自身が検証し失効の仕組みもないので、問題の中間 CA を Go の検証器で拒否するようにした
- Go は検証コードをバイナリに埋め込む（静的リンク）ので、Go を更新しても再ビルドしないと修正は入らない
- アナウンスはあえて詳細をぼかし、攻撃方法が広まる前に守る側が更新する時間を作った

### 4. 自分（SRE）がやること

1. 独自のトラストストアや検証器を持つもの（certifi、Node、Java、Go、コンテナイメージ）を更新し、再ビルド・再起動まで済ませる
2. 確認する

```sh
go version -m ./mybinary             # ビルドした Go が 1.27.3 / 1.26.10 未満なら再ビルド
govulncheck -mode=binary ./mybinary
curl https://dv-g3b-emudhra.we-have-a-problem.com/  # 証明書エラーなら対策済み。繋がったら危険
```

手元の Mac の `/usr/bin/curl` は 200 で繋がった（`/etc/ssl/cert.pem` に G3 が残っている）。

3. エラーが出ても `-k` や `verify=False` で検証を切らない。それは「偽の証明書でも通す」設定そのもの
