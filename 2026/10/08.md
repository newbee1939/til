## ⭐️Go: interfaceは「使う側」で定義する慣習

https://go.dev/wiki/CodeReviewComments#interfaces

> Go interfaces generally belong in the package that uses values of the interface type, not the package that implements those values. The implementing package should return concrete (usually pointer or struct) types: that way, new methods can be added to implementations without requiring extensive refactoring.

- interfaceは、実装するパッケージではなく、その値を使うパッケージに置く
- 実装するパッケージは具象型を返す。そうしておけば、あとからメソッドを足しても大きな書き直しにならない

### 用語

- interface型: 「どんなメソッドを持っているか」だけを決めた型。中身（処理）は無い
  - 例: `Store` =「`Get(id)` ができるもの」
- 具象型（concrete type）: 中身（データと処理）を実際に持っている型。interface型ではない型すべて
  - 例: `int`、`string`、`struct`、`*postgres.DB`
  - 「`Get` ができるもの」が interface型、「実際に `Get` の処理を持っている `*postgres.DB`」が具象型
- 使う側: メソッドを呼ぶ側。下の例では `user`（`s.Get(id)` を呼ぶ）
- 実装側: メソッドの中身を書く側。下の例では `postgres`（`Get` の処理を書く）

### たとえ

- 使う側が「`Get` ができる人なら誰でもOK」という求人票（interface）を出す
- 実装側は求人票を見ずに、ただ `Get` ができる人（具象型）を用意する
- 条件を満たしていれば、そのまま採用される（引数に渡せる）
- 求人票は「雇う側」が書くもの。応募する側が書くものではない、という話

### 具体例

```
myapp/
├── go.mod
├── main.go
├── user/
│   ├── user.go
│   └── user_test.go
└── postgres/
    └── postgres.go
```

`go.mod`

```
module example.com/myapp

go 1.21
```

`user/user.go`（使う側。importが1つも無い = postgres を知らない）

```go
package user

// Store は「id から名前を引けるもの」。user が必要とする分だけを書く。
type Store interface {
	Get(id string) (string, error)
}

// Greet は Store の中身が何であるかを知らない。Get できれば何でもよい。
func Greet(s Store, id string) (string, error) {
	name, err := s.Get(id)
	if err != nil {
		return "", err
	}
	return "Hello, " + name, nil
}
```

`postgres/postgres.go`（実装側。こちらもimportが無い = user も Store も知らない）

```go
package postgres

// DB は具象型。
type DB struct{}

// New は interface ではなく具象型 *DB を返す。
func New() *DB { return &DB{} }

// Get は本物なら SELECT を投げる。ここでは説明用に固定値を返すだけ。
func (*DB) Get(id string) (string, error) {
	return "alice", nil
}
```

- `"alice"` に意味は無い。DBに繋がずに動かすためのダミー値で、`"bob"` でも何でもよい
- 大事なのは値ではなく、`Get(id string) (string, error)` という形が `Store` と一致していること

`main.go`（両方をimportして繋ぐのはここだけ）

```go
package main

import (
	"fmt"

	"example.com/myapp/postgres"
	"example.com/myapp/user"
)

func main() {
	// db は *postgres.DB（具象型）
	db := postgres.New()

	// *postgres.DB は Get を持つので、user.Store としてそのまま渡せる
	msg, err := user.Greet(db, "1")

	fmt.Println(msg, err) // Hello, alice <nil>
}
```

### なぜ postgres は Store を知らなくてよいのか

https://go.dev/doc/effective_go#blank_implements

> a type need not declare explicitly that it implements an interface. Instead, a type implements the interface just by implementing the interface's methods.

- Goには `implements` 宣言が無い。同じ形のメソッドを持っていれば、それだけでinterfaceを満たす
- だから `postgres` は `user` をimportせずに `Store` を満たせる → interfaceを使う側に置ける
- Javaは実装側に `class DB implements Store` と書くので、実装側がinterfaceをimportする必要がある。ここが違い

### 逆に、実装側に置くとどうなるか

`postgres` に `Store` を置くと、`user` は `postgres.Store` と書くために `postgres` をimportすることになる。

```go
package user

import "example.com/myapp/postgres"

func Greet(s postgres.Store, id string) (string, error) { /* 同じ */ }
```

- 業務ロジック（`user`）が、DBの都合（`postgres`）に依存してしまう
- MySQLに替えるとき、`user` 側のimportと型名まで書き換えることになる
- 実装側に置いたinterfaceは「DBができること全部入り」になりがち。使う側は `Get` しか要らないのに

### DIP（依存性逆転の原則）との関係

- DIP: 上位（業務ロジック）が下位（DBなどの詳細）に依存せず、どちらも抽象（interface）に依存する
- 依存 = importのこと。上の具体例のimportは次の2本だけ

```
main ──> user      （Store を持つ）
main ──> postgres  （Store の形に合わせている）
```

- `user` は `postgres` をimportしていない。抽象（`Store`）を上位である `user` が持つので、DIPが自然に成り立つ

### うれしいこと

テストで偽物を渡せる（DB不要）。`user/user_test.go`

```go
package user

import "testing"

// fakeStore はテスト用の偽物。Get を持つので Store を満たす。
type fakeStore struct{}

func (fakeStore) Get(id string) (string, error) { return "bob", nil }

func TestGreet(t *testing.T) {
	got, _ := Greet(fakeStore{}, "1")
	if got != "Hello, bob" {
		t.Fatalf("got %q", got)
	}
}
```

- interfaceが、使う分だけの小さいものになる
