## ⭐️304 ステータスコード

参考: https://developer.mozilla.org/ja/docs/Web/HTTP/Reference/Status/304

「**あなたの持っているコピーはまだ有効。だから本文は送らない**」を意味するレスポンス。

- 条件付き GET / HEAD（`If-None-Match` / `If-Modified-Since` 付き）に対してのみ返る
- **本文を持たない**。代わりに 200 で返すはずだったメタデータ（`ETag` / `Cache-Control` / `Expires` / `Vary` / `Date`）を載せる
- 3xx だがリダイレクトではない。「行き先を変えろ」ではなく「手元のを使え」

### 本文がないと何が得か

- **転送量** — 1MB の CSS/画像が数百バイトで済む。CDN のオリジン転送費に直結
- **サーバー処理** — 本文を生成・読み出さず、バリデーターの比較だけで終わる
- **クライアント処理** — 再パース・再デコードが不要
- **ただし遅延は減らない** — RTT 1 回はかかる。真のキャッシュヒット（リクエストすら出さない）には勝てない

### 「送らない」のではなく「送れない」

RFC 9112 §6.3 で 304 は HEAD 応答や 204 と同じく「ヘッダー後の最初の空行で必ず終端する」と規定されている。
`Content-Length` に何を書いても本文とみなされない。書いてしまうと keep-alive（TCP 接続の使い回し）で繋がっている相手はそれを**次のレスポンスの先頭**として読み始め、以降が壊れる。

## ⭐️HTTP条件付きリクエスト

参考: https://developer.mozilla.org/ja/docs/Web/HTTP/Guides/Conditional_requests

**リクエストに前提条件を付け、満たされたときだけサーバーに実行させる**仕組み。
条件は「リソースが今この状態か？」の判定で、判定材料を **バリデーター**と呼ぶ。

| バリデーター | 正体 |
|---|---|
| `ETag` | サーバーが付けるリソースの版ID |
| `Last-Modified` | 最終更新日時 |

### ETag はどう作られるのか

仕様（RFC 9110 §8.8.3）は中身を決めていない。**サーバーが好きに決める不透明な文字列**で、クライアントは一致するかを見るだけ。実装は 2 派に分かれる。

- **メタデータから作る** — nginx は `"最終更新時刻-サイズ"` を 16 進で並べるだけ（`"689f1a2c-1f4b"`）。本文を読まずに作れて速い
- **本文のハッシュ** — S3 の ETag は基本的に本文の MD5

ハッシュは本文全体を読む必要があるので、静的ファイル配信では前者が選ばれやすい。

### キャッシュ検証で使うヘッダー

| ヘッダー | 成立条件 |
|---|---|
| `If-None-Match` | ETag が**一致しない** |
| `If-Modified-Since` | 指定日時より後に更新された（ETag がない場合の代替） |

## ⭐️304 ステータスコードと HTTP 条件付きリクエスト

`If-None-Match: "abc"` は「**ETag が "abc" と一致しないなら本文をくれ**」というお願い。
つまりここでの条件は「**サーバーが本文を送るための条件**」で、成否で返すものが変わる。

| サーバー側の ETag | 条件 | レスポンス |
|---|---|---|
| `"def"`（変わっていた） | 一致しない → **成立** | `200` + 本文 |
| `"abc"`（変わっていない） | 一致した → **不成立** | `304`（本文なし） |

304 は「条件が成立しなかったので 200 の代わりに返す返事」。
だから**条件付きリクエストを送っていないのに 304 が返ることはない**。

```
1回目: GET /style.css
       → 200 OK  ETag: "abc"  Cache-Control: max-age=600

max-age 経過 → キャッシュは stale になるが破棄はされない

2回目: GET /style.css   If-None-Match: "abc"
       → 304  ETag: "abc"   …本文なし・鮮度だけ更新
       or 200  ETag: "def"   …本文あり・差し替え
```

腹落ちポイントは **キャッシュの期限切れ ≠ 再ダウンロード**。
期限が切れたのは「確認せずに使ってよい期間」だけで、実体は手元に残っている（stale 状態）。
条件付きリクエストはそれを捨てずに「まだ使える？」と**問い合わせだけ**する手段で、304 はその答え。
304 は `Cache-Control` を再送するのでキャッシュは **fresh に戻る**。

逆にバリデーターが無いレスポンスは確認手段がないので期限切れ = 再ダウンロード確定。つまり **ETag を付けることは「キャッシュの寿命を延長する権利」を与えること**に近い。
